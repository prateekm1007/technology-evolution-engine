## 2. Every Design Flaw Discovered

### 2.1 Flaws in the original V1.13 (pre-Gate-1)

**F-01. Broad-range matching made "CORRECT" almost unfalsifiable.**
The original evaluator accepted a prediction as CORRECT if the observed value fell anywhere within a broad range like ">50 cycles" or "[1, 1000]". A range like [1, 1000] is satisfied by 99% of plausible outcomes. This manufactured a 30-40% "discovery" rate from predictions that were essentially unfalsifiable.

**F-02. The novelty check was a 60% term-overlap heuristic.**
The original `novelty_check` flagged a prediction as "novel" if it had < 60% content-term overlap with the evidence. This is far too lenient: a prediction can introduce no genuinely new relation and still pass (e.g., by rephrasing). Gate 1 found 0/40 RECONSTRUCTION with this heuristic; Gate 2's deterministic entailment test found 15/40 (37.5%).

**F-03. The "pre_registration_timestamp" was backdated.**
The original receipt factory accepted an arbitrary `pre_registration_timestamp` parameter. For historical backtests, this was set to the case's cutoff date (e.g., "1990-12-31T23:59:59Z"). This is not a real pre-registration — it is a backdated timestamp. The naming itself overclaimed pre-registration status.

**F-04. The LLM had access to the historical answer via parametric memory.**
The LLM's training data post-dates every cutoff date in the benchmark. The LLM has effectively "seen" the answer for every case (lithium-ion batteries, PCR, CRISPR, mRNA vaccines, etc.). The "evidence" supplied to the LLM was a supplement, not a constraint — the LLM's parametric memory was the primary input.

**F-05. The benchmark was generated FROM known discoveries.**
All 10 cases were selected because they were known historical discoveries. This introduces selection bias: the LLM is being asked to "predict" outcomes it has been trained on. A genuine discovery test must include cases where the outcome is NOT known to anyone (including the experimenters) at registration time.

**F-06. No control was registered at the same time as the treatment.**
The 4 configs (B_llm_only, C_mechanism, F_full, D_random) were all generated by the same LLM with the same evidence. The "random" control (D_random) used a vague prompt ("generate any plausible prediction"), but it still had access to the same evidence and the same parametric memory. This is not a true random control — it is a fourth treatment arm with weaker scaffolding.

### 2.2 Flaws discovered in Gate 1

**F-07. Range fitting survived Gate 1's stricter specificity check.**
Gate 1 added a range-spread check (high/low ≤ 5 for percentages, ≤ 10 for absolute), but this still allowed ranges like [500, 1000] (spread = 2.0) that happened to include the observed value 500 at the lower bound. The 3 surviving Gate 1 DPS=1 receipts (PB-001|D_random, PB-001|F_full, PB-004|F_full) all had lower bounds within 1 unit of the observed value — the signature of range-fitting, not discovery.

**F-08. The information-content test was still string-based.**
Gate 1's information-content test used term-overlap ratio (≥ 70% for explicit, ≥ 55% for trivially-entailed). This is still a string-metric, not a semantic-entailment test. It failed to catch predictions that were near-deterministic consequences of the evidence but used different surface terms. Gate 1 found 0/40 RECONSTRUCTION — suspiciously low, indicating the test was too weak.

**F-09. The legacy_broad_range_match was preserved "for transparency" but enabled continued self-deception.**
By keeping the legacy metric visible alongside the forensic DPS, the report allowed readers to cherry-pick the more favorable number. The 27.5% legacy rate was presented as a point of comparison, but it served as a rhetorical anchor that made the 7.5% forensic rate look like a "stricter cut" rather than a retraction.

### 2.3 Flaws discovered in Gate 2

**F-10. The evidence-only prompt is a SOFT constraint, not a hard one.**
Gate 2's leakage-controlled generator instructed the LLM to "use ONLY the evidence text" and "do NOT use any prior knowledge." But there is no mechanism to enforce this. The LLM's parametric memory is always active. The instruction is a polite request, not a technical constraint. We documented this honestly, but it means Gate 2's 0% DPS=1 rate is an UPPER BOUND on the system's true discovery ability — and even that upper bound is zero.

**F-11. The deterministic entailment test is conservative.**
Gate 2's 6-check entailment test only catches predictions that are *explicitly* or *trivially* encoded in the evidence. It does not catch predictions that are *inferred* from the evidence via multi-step reasoning (e.g., "if X intercalates lithium and Y intercalates lithium, then X+Y is a battery"). Such inferences would pass Gate 2's IC test as GENUINE_NOVEL_PREDICTION even though they are deterministic consequences of the evidence. A stronger test would require an LLM judge, which conflicts with the determinism requirement.

**F-12. The 47.5% INDETERMINATE rate reveals a deeper problem.**
19/40 Gate 2 receipts were classified INDETERMINATE because the LLM's predicted direction type (INCREASE/DECREASE/BINARY) did not match the outcome's direction type (e.g., predicting INCREASE for a BINARY outcome). This is not a scoring artifact — it is a real signal that the LLM is not even producing directionally-aligned predictions for those cases. The LLM is generating syntactically valid JSON that is semantically incoherent with the outcome space.

**F-13. The point-estimate requirement made the calibration error brutally honest.**
Without broad ranges to hide behind, the LLM's point estimates were off by orders of magnitude. Of 21 numeric GENUINE_NOVEL_PREDICTION receipts, 17 had calibration_error > 1.0 (i.e., the predicted value was more than 2× the observed value, or less than half). The LLM does not actually know the magnitudes — it only knows the directions and the entities.

**F-14. The "frozen model" was never actually frozen.**
Gate 2 used the `z-ai` CLI (glm-4-plus) as the backend. This is a hosted model that can be updated by the provider at any time. We have no guarantee that the model weights were the same across all 40 generation calls, let alone across re-runs. A genuinely frozen model requires either (a) a local model with pinned weights, or (b) a hosted model with a version-pinned endpoint.

### 2.4 Structural flaws (apply to all of V1.13)

**F-15. Retrospective backtesting cannot establish discovery.**
The fundamental flaw: in a retrospective backtest, the experimenter already knows the answer. This knowledge leaks into the benchmark design (case selection, evidence phrasing, outcome specification) even if it does not leak into the LLM prompt. The experimenter's confirmation bias is unavoidable in retrospective designs.

**F-16. The benchmark cases were not independently selected.**
The 10 cases were chosen by the experimenter because they were famous discoveries. This means the evidence text, the cutoff date, and the outcome specification were all shaped by the experimenter's knowledge of how the story ended. An independent case-selection protocol would require cases to be selected by someone who does not know the outcome — which is impossible in a retrospective design.

**F-17. The "North Star" question was being asked of the wrong system.**
The North Star asks: "Can TEE produce independently novel, retrieval-negative, adversarially surviving, falsifiable hypotheses at a materially higher rate than controls?" The key word is **independently novel** — meaning novel with respect to the entire state of human knowledge at registration time, not just novel with respect to the supplied evidence. A retrospective backtest cannot establish independent novelty because the LLM has the entire state of human knowledge in its parametric memory.

## 5. Why Retrospective LLM Evaluation Cannot Establish the North Star

### 5.1 The North Star, restated

> "Can TEE produce independently novel, retrieval-negative, adversarially surviving, falsifiable hypotheses at a materially higher rate than controls?"

The key phrase is **independently novel** — novel with respect to the entire state of human knowledge at registration time.

### 5.2 Three reasons retrospective evaluation fails

**Reason 1: Parametric memory leakage is unavoidable.**
Every modern LLM has been trained on a corpus that includes the historical outcome of every famous discovery. The LLM "knows" that lithium-ion batteries work, that PCR achieves million-fold amplification, that CRISPR enables gene editing. No prompt instruction can disable this knowledge — it is baked into the weights. The evidence supplied to the LLM is a supplement to its parametric memory, not a constraint on it. Every "prediction" the LLM makes is contaminated by foreknowledge of the answer.

**Reason 2: Experimenter bias is unavoidable in case selection.**
In a retrospective backtest, the experimenter selects cases. The experimenter knows which discoveries succeeded and which failed. This knowledge shapes:
- Which cases are selected (only famous successes)
- How the evidence is phrased (foregrounding the elements that turned out to matter)
- Where the cutoff date is set (just before the "key" insight)
- How the outcome is specified (the metric that the discovery happened to optimize)

Even with the best intentions, the experimenter cannot avoid this bias. The only way to avoid it is to not know the outcome at case-selection time — which is impossible in a retrospective design.

**Reason 3: There is no true control.**
A true control would be a system that cannot possibly know the answer. In a retrospective design, the "random" control (D_random) uses the same LLM with the same parametric memory. The only difference between treatment and control is the prompt scaffolding — not the information available. This means any observed difference between treatment and control is measuring prompt-engineering, not discovery ability.

### 5.3 The logical structure of the failure

The North Star requires:
1. The prediction is novel with respect to human knowledge at time T.
2. The prediction is later observed to be correct at time T' > T.

In a retrospective backtest:
- The LLM's knowledge cutoff is T_LLM >> T (for all cases).
- The experimenter's knowledge at case-selection time is T_exp >> T.
- The "observation" at T' is already known to both LLM and experimenter.

There is no point in the timeline at which the prediction is genuinely novel. The retrospective backtest is testing whether the LLM can *reconstruct* a known discovery from curated evidence — not whether it can *discover* anything.

### 5.4 Why no amount of forensic tightening fixes this

Gate 1 tightened the scoring. Gate 2 tightened the information-content test and the leakage control. Both gates reduced the DPS=1 rate (30% → 7.5% → 0%). But no amount of tightening can address the structural problem: the LLM knows the answer, the experimenter knows the answer, and the "prediction" is being evaluated against a known answer.

The Gate 2 result (0% DPS=1) is the most honest result we obtained — and it is consistent with the structural argument. Even with the upper-bound advantage of parametric-memory leakage, the system produces zero discoveries under strict criteria. This is not because the system is bad at discovery; it is because the experimental design cannot measure discovery.

## 6. What Evidence Would Be Required for a Valid Prospective Test

### 6.1 The minimal requirements

**Requirement P-01. Real pre-registration.**
The prediction must be registered (with a timestamp from a trusted time source) BEFORE the outcome is observed by anyone. The registration must include:
- The full prediction text
- The falsification condition
- The quantitative tolerance
- The model snapshot identifier (weights hash or version pin)
- The retrieval corpus hash (if retrieval is used)
- The full prompt template
- The random seed

The registration must be tamper-evident: any modification after registration must be detectable. This requires either a blockchain-style append-only log or a trusted third-party timestamping service.

**Requirement P-02. Frozen model snapshot.**
The model weights must be fixed BEFORE registration. If using a hosted model, the endpoint must be version-pinned (e.g., `claude-3-opus-20240229`, not `claude-3-opus`). If using a local model, the weights file must be hash-sealed. The snapshot identifier must be included in the pre-registration manifest.

**Requirement P-03. Frozen retrieval corpus.**
If the system uses retrieval, the corpus must be frozen BEFORE the prediction is generated. The corpus hash must be included in the pre-registration manifest. No updates to the corpus are permitted between registration and observation.

**Requirement P-04. No historical answer supplied to the generator.**
The generator must not be given any information about the outcome. This includes:
- Not telling it which case it is predicting
- Not giving it evidence that was curated with knowledge of the outcome
- Not giving it a "hint" about the expected direction or magnitude

The only input should be a problem description and a frozen corpus to retrieve from.

**Requirement P-05. Future evidence inaccessible until observation window closes.**
The system must not have access to any evidence dated after the registration timestamp. This requires either:
- A corpus with strict date filtering (and a verification that the filter works)
- A retrieval system that physically cannot access post-registration documents

**Requirement P-06. External outcomes from sources outside the engine.**
The outcome must come from a source that is independent of the engine. This means:
- Not the experimenter's own measurement
- Not a source that the experimenter controls
- A source that publishes the outcome in a way that the engine cannot influence

Acceptable sources: peer-reviewed publications, public databases, regulatory filings, independent replication studies.

**Requirement P-07. Controls registered at the same time as treatment.**
All four arms (LLM-only, mechanism-only, full system, random) must be registered in the same pre-registration manifest, with the same timestamp, the same model snapshot, the same corpus, the same prompt templates (modulo the treatment-specific scaffolding). This ensures that any difference between arms is attributable to the scaffolding, not to confounding variables.

**Requirement P-08. Do not generate the benchmark from known discoveries.**
The benchmark cases must NOT be selected because they are known discoveries. They must be selected by a process that is independent of the discovery outcome. Options:
- Random sampling from a problem space (e.g., "all materials-science problems proposed in 2024")
- Selection by an independent party who does not know which problems will be solved
- Selection from a pre-existing registry (e.g., a DARPA problem set) that was created before the engine existed

**Requirement P-09. Pre-register the analysis before observing outcomes.**
The statistical analysis plan must be fixed BEFORE any outcomes are observed. This includes:
- The primary endpoint (e.g., DPS=1 rate)
- The comparison (treatment vs. control)
- The significance threshold (α)
- The minimum detectable effect size
- The sample size and power calculation
- The handling of INDETERMINATE cases (e.g., excluded, counted as failure)

The analysis plan must be included in the pre-registration manifest.

**Requirement P-10. Independent reproducibility.**
The entire pipeline must be reproducible by an independent auditor. This requires:
- All code is open-source and version-pinned
- All manifests are hash-sealed and publicly archived
- All timestamps are from trusted sources
- The audit trail is append-only and tamper-evident

### 6.2 What the prospective experiment would look like

```
PRE_REGISTER
    ├── Register problem set (selected independently of outcomes)
    ├── Register model snapshot (frozen weights, hash-sealed)
    ├── Register retrieval corpus (frozen, hash-sealed)
    ├── Register prompt templates for all 4 arms
    ├── Register analysis plan (α, MDE, sample size, handling of INDETERMINATE)
    └── Register timestamp (trusted source, tamper-evident)
        ↓
FREEZE_MODEL
    └── Verify model snapshot matches registered hash
        ↓
FREEZE_EVIDENCE
    └── Verify retrieval corpus matches registered hash
    └── Verify date filter excludes post-registration documents
        ↓
GENERATE_PREDICTION (4 arms, in parallel, same timestamp)
    ├── LLM-only: prompt = problem + frozen corpus
    ├── Mechanism-only: prompt = problem + frozen corpus + mechanism scaffolding
    ├── Full system: prompt = problem + frozen corpus + full scaffolding
    └── Random: prompt = problem + frozen corpus + vague instruction
    └── Each arm produces: hypothesis + prediction + falsifier + tolerance
    └── Each prediction receipt is hash-sealed and appended to the log
        ↓
WAIT (until observation window opens)
    └── No engine activity permitted
    └── Observation window is pre-registered (e.g., "12 months after registration")
        ↓
EXTERNAL_OBSERVATION
    └── Outcome is collected from a source outside the engine
    └── Outcome source is pre-registered (e.g., "peer-reviewed publication in journal X")
    └── Outcome is hash-sealed and appended to the log
        ↓
DETERMINISTIC_SCORE
    └── Scorer is the same as Gate 2 (deterministic, no LLM judge)
    └── Applies the pre-registered analysis plan
    └── Produces: DPS=1 rate per arm, calibration error, IC score
    └── Results are hash-sealed and appended to the log
```

### 6.3 What would constitute a positive result

A positive result would require ALL of:
1. At least 3 GENUINE_NOVEL_PREDICTION cases across the treatment arm (gate 1 of the exit criterion).
2. The treatment arm's DPS=1 rate materially exceeds the random control's DPS=1 rate by ≥ 15 percentage points (gate 2 of the exit criterion).
3. The result is statistically significant at α = 0.05 with the pre-registered sample size.
4. The calibration errors of CORRECT cases are ≤ 0.50 (the predictions are quantitatively accurate, not just directionally correct).
5. An independent auditor can reproduce the entire pipeline from the pre-registration manifest.

If any of these fails, the result is negative. No discovery signal is manufactured.
