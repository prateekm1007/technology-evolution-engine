# NULL_CONTROL_SPEC_V1

**Date:** 2026-08-11
**Status:** MANDATORY CORRECTION

## The False Signal

The V1.1 audit reported:

```
REAL: 11/11 survive adversarial review (100%)
NULL: 0/47 survive adversarial review (0%)
Discovery Signal: 100%
```

**This is NOT a 100% discovery signal.** It is a **pipeline separability test** — the system trivially distinguished its own generated candidates from deliberately nonsensical random pairs.

### Why this is not discovery evidence

1. **The null generator is structurally different from the real generator.** Real candidates come from discovery operators with mechanistic framing. Null candidates come from `random.choice()` with no mechanistic basis. The self-attacker can trivially tell them apart by checking `is_null_control: True` or by inspecting the `bridge: "NONE — randomly paired"` field.

2. **The self-attacker knows nulls have no mechanistic basis.** Attack #5 ("Is the analogy superficial?") returns `"FATAL — no mechanistic basis"` for nulls but `"LIKELY"` for real candidates. This is not adversarial evaluation — it's pattern matching on the candidate's metadata.

3. **A system that trivially distinguishes its own generated candidates from deliberately nonsensical random pairs has not demonstrated discovery.** This is the easiest possible discrimination task. Any classifier that reads the `bridge` field would achieve 100% accuracy.

### What would constitute discovery evidence

Discovery evidence requires:

1. **Hard negatives** — null candidates that are lexically/semantically convincing but mechanistically incompatible. The system should struggle with some of these.

2. **Blind evaluation** — the attacker must not know which candidates are real vs null. Currently the attacker can see `is_null_control: True`.

3. **Equal information budget** — all controls (LLM, retrieval, embedding, BM25) must receive the same evidence universe and token budget.

4. **Independent adjudication** — human reviewers must classify outputs without knowing which system generated them.

5. **Historical blind discovery** — the system must generate connections that were LATER discovered by humans, using only information available BEFORE the discovery.

---

## Hard Null Types (Required)

The null generator must produce these 6 types of hard negatives:

### NULL-1: Lexically convincing but mechanistically incompatible
Pairs selected because titles/abstracts have high lexical similarity but no demonstrated mechanistic relationship. Example: two papers both mention "surface modification" but one is about corrosion prevention and the other is about optical coatings — the shared term doesn't imply transferability.

### NULL-2: Mechanistically similar but boundary-condition incompatible
Pairs where the mechanism is the same type but the operating conditions are incompatible. Example: a high-temperature catalytic process and a low-temperature biological process — both "catalytic" but the boundary conditions make transfer impossible.

### NULL-3: Cross-domain pairs where the apparent transfer has known failure
Pairs where someone has already tried the transfer and it failed. Example: using battery electrolyte chemistry in biological systems — known to be toxic.

### NULL-4: Pairs where the relationship is already explicitly established
Pairs where the connection is already well-known. These should be classified as KNOWN, not as discoveries. Example: using polymer science in drug delivery — already a well-established field.

### NULL-5: Pairs where the proposed mechanism is physically impossible under target conditions
Pairs that violate physical laws under the target domain's conditions. Example: proposing a high-pressure process for a system that operates at atmospheric pressure.

### NULL-6: Pairs generated by the LLM baseline but rejected by expert review
Pairs that the LLM thinks are interesting but that human experts have rejected. These calibrate the LLM's false-positive rate.

## What the Null Generator Must NOT Do

- ❌ Must NOT set `is_null_control: True` in a way the attacker can see
- ❌ Must NOT use `bridge: "NONE — randomly paired"` — the bridge field must be filled with a plausible-sounding (but wrong) mechanistic bridge
- ❌ Must NOT use `epistemic_state: "NULL_CONTROL"` — the state must be `CANDIDATE_CONNECTION` to match real candidates
- ❌ Must NOT have `candidate_hypothesis` that mentions "random" or "null"

The null candidates must be **indistinguishable from real candidates by metadata inspection**. The attacker must evaluate them on their scientific merits alone.

---

## Acceptance Criteria

The null control is only valid when:

1. Null candidates pass the same structural schema as real candidates
2. The attacker cannot identify nulls by metadata alone
3. Some nulls survive the attacker (hard negatives that fool the system)
4. Some real candidates are killed by the attacker (the attacker is discriminating)

If 100% of nulls are killed and 100% of reals survive, the test is still pipeline separability, not discovery evidence.

**Target: The system should struggle with at least 20% of hard negatives.** If it rejects 100% of hard negatives, the hard negatives aren't hard enough. If it accepts many, that is valuable failure evidence.
