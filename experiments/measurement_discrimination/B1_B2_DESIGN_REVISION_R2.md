## 1. B2 Null-Generating Process (FATAL fix)

### The problem
R1 specified McNemar's test for B2 (engine vs null, paired by case) but never defined how the B2 null candidate is generated. B2 has no gold answer, so the B1 null approach (recombine from other cases' gold mechanisms) is not applicable.

### The distinction: recognition null vs generation null

**Recognition null (adjudication control):** A candidate is constructed by the researcher and submitted to adjudicators. Tests whether adjudicators reject corrupted candidates. Does NOT test whether the engine's generation process has a low false-discovery rate.

**Generation null (discovery counterfactual):** A candidate is generated by a comparable process that lacks the capability being tested. Tests what the engine's yield would be if it did not possess the discovery capability. This is the counterfactual the North Star requires.

### B2 null architecture: independent null arm (Option B from audit)

B2 uses an **independent null arm** rather than a matched procedural null, because:
- B2 has no gold answer, so "recombining from other cases' mechanisms" is not applicable
- A procedural null (modifying the engine's output) would be a recognition null, not a generation null
- An independent null arm allows a genuine counterfactual: "what yield would a system without the engine's cross-domain synthesis capability produce?"

### B2 null-generating process

The null arm uses the **retrieval-only baseline** as the generation null:

```
NULL ARM:
    Source A → NLP entity extraction → entities_A
    Source B → NLP entity extraction → entities_B
    ↓
    discover_shared_entities(entities_A, entities_B) — entity intersection only
    ↓
    For each shared entity, construct a candidate:
        "The shared concept '{entity}' connects domain A and domain B
         through {entity}'s role in both systems."
    ↓
    First 3 candidates (by entity extraction order) retained
    ↓
    Adjudicated under identical Gate A/B/C procedure
```

### Why this is a generation null
The retrieval-only arm generates candidates from the SAME source material using a process that lacks the engine's mechanism extraction, abstraction, transfer, and hypothesis generation pipeline. It finds shared entities (retrieval) but does not generate cross-domain mechanisms (discovery).

### Why this is a valid counterfactual
If the engine's yield is not significantly different from the retrieval-only yield, the engine's "discoveries" are indistinguishable from entity intersection — which the SCIENTIFIC_GATE_2_PROTOCOL.md explicitly says is NOT discovery.

### Statistical implication
Because the null arm is an **independent arm** (different generation process, same source pairs but independently generated candidates), the observations are NOT paired at the candidate level. However, they ARE paired at the **case level** (same source pair produces one engine outcome and one null outcome).

### Revised statistical test for B2

```
Case-level pairing:
    Case i: engine_success_i (0/1), null_success_i (0/1)

Test: McNemar's exact test (one-sided, engine > null)
    b = #(engine=1, null=0)
    c = #(engine=0, null=1)
    p-value = P(Binomial(b+c, 0.5) ≥ b) (one-sided)

α = 0.05
```

This is valid because:
- Each case produces one binary outcome for the engine (did ≥1 of ≤3 candidates pass all gates?)
- Each case produces one binary outcome for the null (did ≥1 of ≤3 retrieval candidates pass all gates?)
- The pairing is at the case level (same source pair)
- The outcomes are binary (success/failure)

### What the null tests
The null tests: "If the engine's mechanism-generation pipeline were replaced with simple entity intersection, would the yield of adjudicated-valid discoveries be the same?"

If yes → the engine's pipeline adds no value over retrieval → NOT discovery.
If no (engine > null) → the engine's pipeline produces discoveries that retrieval cannot → discovery signal detected.

## 2. Recognition vs Generation Nulls (Separation)

### B1 null = recognition/adjudication control

B1's null (recombined candidate from other cases) is explicitly classified as a **recognition/adjudication control**:

```
B1 RECOGNITION CONTROL:
    Purpose: Test whether adjudicators reject deliberately corrupted candidates
    Generation: Human/researcher modifies the engine's true candidate
    What it measures: Adjudicator rejection rate for corrupted candidates
    What it does NOT measure: Engine false-discovery rate
    Endpoint name: CORRUPTED_CANDIDATE_REJECTION_RATE
```

### B1 generation null = retrieval-only arm

B1 ALSO includes the retrieval-only arm as a **generation null**:

```
B1 GENERATION NULL:
    Purpose: Test what yield retrieval-only would produce on B1's source pairs
    Generation: Same source pairs, entity intersection only (no mechanism generation)
    What it measures: Whether the engine's pipeline outperforms retrieval on known relationships
    What it tests: "Can the engine recover known mechanisms better than entity intersection?"
    Endpoint name: RETRIEVAL_RECOVERY_RATE
```

### B1 primary comparison revised

```
B1 primary = engine recovery rate vs retrieval recovery rate
    (Can the engine's pipeline recover known mechanisms better than retrieval?)

B1 secondary = corrupted candidate rejection rate
    (Do adjudicators reject deliberately corrupted candidates?)
```

The corrupted candidate rejection rate is a **quality control metric for the adjudication process**, not a discovery metric. It is reported but NOT used in the primary discovery decision.

## 3. B1 Null Endpoint Renamed

### Before (R1)
```
null_FP_rate ≤ 0.20
```
This overclaims: it implies the null measures the engine's false-positive rate.

### After (R2)
```
CORRUPTED_CANDIDATE_REJECTION_RATE ≥ 0.80
```
This accurately describes what is measured: the fraction of deliberately corrupted candidates that adjudicators REJECT.

Note the direction change: R1 required `null_FP ≤ 0.20` (low false-positive). R2 requires `rejection ≥ 0.80` (high rejection). These are mathematically equivalent (rejection = 1 - acceptance) but the naming is epistemically honest.

### Revised B1 decision partition

```
IF leakage_check == FAILED:
    INCONCLUSIVE_LEAKAGE

ELSE IF N_clean < 10:
    INSUFFICIENT_CLEAN_CASES

ELSE IF null_validity == FAILED:

ELSE IF beautiful_nonsense_control == FAILED:

ELSE IF calibration_kappa < 0.40:
    PROTOCOL_NOT_READY

ELSE IF recovery_rate ≥ 0.40
     AND retrieval_recovery_rate < recovery_rate
     AND corrupted_candidate_rejection_rate ≥ 0.80:
    REDISCOVERY_CAPABILITY_ESTABLISHED (pilot)

ELSE:
    REDISCOVERY_NOT_ESTABLISHED
```

The primary comparison is now engine recovery vs retrieval recovery (generation null). The corrupted candidate rejection rate is a secondary quality gate.

## 4. Beautiful-Nonsense Control Construction (Frozen Independently)

### The problem
R1 said "select domains with NO plausible cross-domain connection" but this requires a human judgment that contradicts B2's rule that the selector does NOT assess plausibility.

### Revised construction protocol

```
BEAUTIFUL-NONSENSE CONTROL SET CONSTRUCTION:

1. MECHANICAL PAIR GENERATION:
   - Generate 100 candidate domain pairs by random selection from
     a predefined domain universe (seed=42)
   - Domain universe: list of ≥ 50 scientific domains (physics, chemistry,
     biology, materials science, computer science, medieval literature,
     poetry, culinary arts, etc.)

2. INDEPENDENT PLAUSIBILITY CLASSIFICATION:
   - 3 independent experts (NOT engine builders, NOT study adjudicators)
   - Each expert independently classifies each pair as:
     PLAUSIBLE_CROSS_DOMAIN / IMPLAUSIBLE / UNCERTAIN
   - Experts receive: domain A name, domain B name, 1-sentence description
   - Experts do NOT receive: source texts, engine outputs, study cases

3. PREREGISTERED AGREEMENT THRESHOLD:
   - A pair is classified as IMPLAUSIBLE if all 3 experts agree
   - A pair is classified as PLAUSIBLE if all 3 experts agree
   - All other pairs = UNCERTAIN (excluded from control set)

4. FREEZE:
   - Select 5 IMPLAUSIBLE pairs (random, seed=42)
   - Freeze the control set (SHA recorded)
   - Experts who classified the control set do NOT adjudicate study candidates

5. CONTROL EXECUTION:
   - Run the engine pipeline on each implausible pair (same as B2)
   - Adjudicate candidates under identical Gate A/C procedure
   - If any candidate passes Gate C: the adjudication process accepted
     a meaningless mechanism → RUBBER_STAMP detected
```

### Inter-rater reliability for control classification
- Cohen's kappa on the 3-expert classification (calculated on all 100 pairs)
- If kappa < 0.40: control set construction is unreliable → PROTOCOL_NOT_READY
- Kappa calculated BEFORE study execution

### What the beautiful-nonsense control tests
"Can the adjudication process distinguish genuine mechanisms from plausible-sounding nonsense generated by the engine on domain pairs where no meaningful cross-domain mechanism exists?"

If Gate C PASS rate on implausible pairs is high → adjudicators are rubber-stamping → all study results are uninterpretable.

## 5. Exact Paired Effect Estimator and CI

### The problem
R1 said "exact binomial 95% CI for the difference in paired proportions" but did not specify the exact method. For paired binary outcomes, the appropriate interval is not a simple binomial.

### Exact specification

#### Estimator
For paired binary outcomes (engine_success, null_success) per case:

```
N = number of cases
b = #(engine=1, null=0)  — discordant pairs favoring engine
c = #(engine=0, null=1)  — discordant pairs favoring null

Point estimate of effect:
    θ̂ = (b - c) / N

This is the difference in marginal proportions:
    θ̂ = P(engine=1) - P(null=1)
```

#### Confidence interval

**Exact McNemar confidence interval** based on the exact binomial distribution of `b` conditional on `b + c`:

```
Given n_d = b + c (total discordant pairs),
b ~ Binomial(n_d, 0.5) under H0: θ = 0

Exact 95% CI for θ:
    Lower: (2 * b_l - n_d) / N
    Upper: (2 * b_u - n_d) / N

where b_l and b_u are the exact binomial quantiles:
    b_l = Binomial_quantile(α/2, n_d, 0.5)
    b_u = Binomial_quantile(1 - α/2, n_d, 0.5)
```

This is implemented in `statsmodels.stats.contingency_tables.mcnemar` with `exact=True` and `correction=False`.

#### Implementation specification
```python
from statsmodels.stats.contingency_tables import mcnemar

# Build 2x2 contingency table:
#                    null_success=0   null_success=1
# engine_success=0       a                c
# engine_success=1       b                d

result = mcnemar(table, exact=True, correction=False)

# Point estimate:
theta_hat = (b - c) / N

# p-value (one-sided, engine > null):
p_value = result.pvalue / 2  # mcnemar returns two-sided; divide for one-sided

# CI: exact binomial on discordant pairs
# Use scipy.stats.binom for exact quantiles
```

#### What if N is very small?
If `b + c < 5` (very few discordant pairs), the exact CI will be very wide. This is reported honestly:
```
if b + c < 5:
    report: "Insufficient discordant pairs for reliable CI estimation.
             Point estimate: θ̂ = {theta_hat}. N_discordant = {b+c}."
```

## Candidate-Level Adjudication Rule (Clarification per Finding #6)

```
Generate ≤3 candidates per case
    ↓
FREEZE all candidates (no further generation)
    ↓
Adjudicate ALL candidates independently (no early stopping)
    ↓
Aggregate to case-level binary outcome:
    case_success = 1 if ANY candidate passes all required gates
    case_success = 0 otherwise
```

No candidate-level early stopping. All ≤3 candidates are adjudicated before aggregation.

## Candidate Ordering (Clarification per Finding #5)

```
Candidate ordering is determined by pipeline output order.
Pipeline output order is deterministic because:
    - temperature = 0.0 (all LLM calls)
    - seed = case_index (preregistered per case)
    - no concurrency in the pipeline
    - no dictionary-order-dependent iteration (uses ordered data structures)
    - no asynchronous execution

If the pipeline's output order is found to be nondeterministic
(verified by running the same case twice and comparing output order):
    → EXPERIMENT = INVALID
    → rerun with verified-deterministic pipeline
```
